## Fonctionnalités (système / kernel)

| Idée | Statut | Notes |
|------|--------|-------|
| IPC : mécanisme de communication inter-processus | 💡 | Brique de base. À terme : déporter le serveur graphique (compositeur, gestion fenêtres, souris, clavier) dans un exécutable séparé. |
| Réseau : exposer la pile TCP/IP de Circle | ✅ | Fait (phase 1, cœur principal) : WLAN `bcm4343` + `wpa_supplicant` + `CNetSubSystem` (DHCP) montés dans un `CNetBringupTask` non bloquant ; sockets TCP via l'ABI v21 (`net_status`/`tcp_connect`/`tcp_send`/`tcp_recv`/`tcp_close`), backend `kernel/sys/net.cpp`. **Reste :** faire tourner la pile sur un **cœur dédié** (phase 2 : `CMultiCoreSupport` + files inter-cœurs). |
| Réseau : résolveurs ARP / DNS, etc. | ✅ | Fournis par la pile Circle : ARP/ICMP internes ; DNS via `CDNSClient` (utilisé par `tcp_connect` quand l'hôte est un nom). |
| Réseau : synchro date/heure via NTP | ✅ | `CNTPDaemon` démarré dès que le lien est up ; `system.ini` `timezone=` (minutes UTC) + `ntp=`. **Réf. :** `circle/sample/18-ntptime`. |
| Classe `HttpClient` (lib) | ✅ | `user/httpc.h` : header-only, sans allocation (buffer fourni par l'appelant), sur les sockets TCP v21. `http_request(method,url,headers,body,…)` (GET/POST/PUT/… via le verbe) + raccourcis `http_get`/`http_post`. HTTP/1.0, pas de HTTPS. Socle du futur navigateur web. |
| Floating point pour les tâches | 💡 | Explorer l'activation du **FPU/SIMD (NEON)** côté user. Implique d'**adapter la sauvegarde/restauration du contexte des tâches** (registres `V0–V31` + `FPCR`/`FPSR`) lors des changements de contexte. À évaluer : coût perf vs lazy-save. |
| Compositor : dirty-rect + flush async | ✅ | Rectangles modifiés (`ScreenDirtyRect`, fusion, ≤ 16) redessinés avec clip (`GImage::SetClip`) et envoyés seuls à l'écran (patch Circle `UpdateDisplay (x, y, w, h)`) ; une fenêtre opaque qui couvre la zone évite de redessiner ce qui est dessous. Reste possible : flush asynchrone (DMA sans attente). |
| Stack OpenGL / GLES (VideoCore) | 💡 | Exposer une **accélération 3D** via le GPU **VideoCore VI** (V3D) du RPi4. Prérequis de plusieurs apps : *Quake III*, émulateurs 3D, futur rendu accéléré. Piste : addon `circle/addon/vc4` (+ Mesa/V3D). Gros morceau ; sans lui, ces apps restent en soft-render (ou hors de portée). |
| Compositor : blits par DMA 2D | 💡 | Évaluer l'usage du **DMA en mode 2D** (transferts avec stride source/dest, BCM2711) pour blitter les **fenêtres → bureau** et les **conteneurs → leur fenêtre**, au lieu de copies CPU. Décharge le CPU sur les grandes surfaces. Voir le contrôleur DMA de Circle (`CDMAChannel`, mode 2D). Complémentaire du dirty-rect. |
| Port audio : synth FM + tracker | ✅ | **Fait** : voix FM 2 opérateurs façon OPL2 (kapi v47), **FM Tracker** (8 canaux, fichiers FM Song .FMS/.FMI) et un lecteur .FMS pour Windows (`tools/fmsplayer`). Base : sortie PWM (jack), producteur sur le cœur 1, kapi v46 (16 voix square/sine/triangle/saw/noise + flux PCM, propriétaire exclusif), BASIC `PLAY`/`SOUND`/`NOTEON`. Reste : Amener le synth FM + tracker dans Onyx. Fixed-point + PWM. |
| Autres langages sur la VM BASIC | 💡 | Le bytecode de la VM (`user/basic`) est générique : d'autres compilateurs peuvent le produire, et `/bin/basic` + les `.bax` deviennent un runtime commun. **Langage façon C#** (classes, héritage, méthodes virtuelles, `try`/`catch`/`finally`, `List<T>`, interpolation). **Mini-PHP** (typage dynamique, tableaux associatifs ordonnés, `foreach`, classes, `include`, les fonctions de chaînes courantes) — avec le *Serveur HTTP simple*, des pages `.php` servies par Onyx. Briques VM à ajouter : objets par référence, tables de méthodes + appel virtuel, pile de points de reprise façon `setjmp` (exceptions, `ON ERROR`), tables de hachage, opérations à typage dynamique. (Le **vrai PHP** — `php-src`, en C — serait plutôt un portage natif newlib, comme NetSurf.) |
| Noyau plus préemptif | ✅ | Fait : E/S fichiers par morceaux de 64 Ko + `Yield` ; le pilote SD rend la main pendant qu'il attend la carte (crochets faibles dans le fork Circle, verrou FatFs « dormant » `sys/fslock.cpp`, section anti-kill) ; le journal n'est plus dessiné sur la console de démarrage cachée (≈ 170 ms IRQ masquées par ligne) ; **détecteur de blocage** (`stall:` dans `kmsg` si une tâche garde le CPU > 100 ms, avec PC/LR). Préemption complète du code noyau : écartée (pilotes Circle, FatFs, pile réseau supposent le coopératif). |
| Cœurs d'app (2 et 3) | ✅ | Une app **acquiert** le cœur 2 ou 3 (kapi v51 `core_acquire` / `core_run` / `core_state` / `core_release`) et y exécute une fonction de son propre code, dans son espace d'adressage, sans ordonnanceur ni interruption (arrêt par IPI, fautes rattrapées, libération à la fin de l'app). Règle : pas d'appel kapi ni d'allocation sur ce cœur. `user/emucore.h` : la machine des émulateurs y tourne (triple tampon d'images, anneau audio, pause entre deux images) ; `gbemu` et `gbaemu` l'utilisent ; test `/bin/coretest`. |
| VM BASIC sur un cœur d'app | 💡 | Faire tourner la VM BASIC (`user/basic`) sur un cœur d'app : le calcul pur (boucles, chaînes, tableaux) et le dessin dans le canevas de la fenêtre y iraient à pleine vitesse, mais chaque instruction qui appelle la kapi (`PRINT` vers la console, fichiers, son, `INKEY$`, `present`, minuteries) devrait être **transmise** au fil principal (file de requêtes + réveil, comme `emucore.h`), les événements (`ON KEY`, `ON TIMER`) remonter dans l'autre sens, et la VM aurait besoin de **son propre tas** (le `malloc` n'est pas multi-cœur). Gain surtout pour les programmes BASIC qui calculent beaucoup (jeux). |
| Bureau distant par fenêtres (rdpd) | ✅ | `rdpd` (port 3390, kapi v56 `win_list` / `win_read` / `win_raise` / `win_close`) + client Windows `pc/OnyxRemote` (.NET 4.8) : chaque fenêtre Onyx devient une fenêtre du PC (son cadre + son contenu), composée côté PC ; seules les fenêtres modifiées et leurs tuiles 64 × 64 changées sont envoyées, en LZ4, 32 ou 16 bits ; souris en coordonnées de la fenêtre (rdpd la replace sur l'écran du Pi), clavier (keysyms partagés avec vncd, caractères selon la disposition du PC). Test hôte `tools/tests/run_rdpd_test.sh`. À faire : le son d'Onyx sur le PC, la manette. |
| JIT pour la VM BASIC | 💡 | Pour plus tard. Un **JIT dans le runtime** (plutôt qu'un compilateur ARM : les `.bax`, l'IDE et les outils Windows restent tels quels) : bytecode → AArch64 au chargement / par SUB, en réutilisant kapi v58 `code_alloc` et l'assembleur de `gc_jit.cpp` ; le natif pour l'arithmétique, les variables, les tableaux, les boucles et les appels, les instructions du runtime (PRINT, fichiers, graphismes) appelées comme aujourd'hui. Préalables : des opcodes typés (entier / simple / double / chaîne) émis par le compilateur, des points de contrôle sur les sauts arrière (`ON TIMER` / `ON KEY` / Ctrl-Break), une table adresse → ligne pour `ON ERROR` / `ERL` ; validation par un fuzzer JIT contre VM. Gain attendu : ×10 et plus sur le calcul en BASIC (fractales, 3D logicielle, simulations, génération procédurale), **quasi nul sur planets3d et Arkanoid** (limités par la synchro, le GPU et des primitives déjà natives). **Première étape** : mesurer, un compteur du temps passé dans la VM contre les primitives natives et les pauses, affiché par le runtime. |
| Émulateur GameCube | 🔨 | **En cours** : cœur `user/gc` — Gekko (PowerPC 750CL) interprété, validé contre qemu-ppc (10 485 résultats identiques) + paired singles ; mémoire / BAT ; PI, VI, SI, EXI, DI, AI / DSP ; FIFO GX + PE ; rendu GX en HLE vers le GPU (sommets, XF, éclairage, texgen, TEV par sommet, 11 formats de texture) ; boot des .dol et des disques via leur apploader ; app `gcemu` (disque lu à la demande : kapi v57 `seek` + FatFs fast seek), bannières dans la Game Library. **JIT PowerPC → AArch64 ✅** (`gc_jit.cpp`, kapi v58 `code_alloc` : mémoire RWX) : entiers, branchements, loads/stores (MEM1 direct), FPU et paired singles en NEON (deux moitiés à la fois), `psq_l`/`psq_st` spécialisés sur le GQR (types entiers compris), `lmw`/`stmw`/`dcbz`, registres PPC gardés en registres ARM par bloc, blocs chaînés, décompte des cycles en registre, chemins rares hors du code principal, boucles d'attente sautées jusqu'au prochain événement, write-gather pipe par salves de 32 octets ; validé contre l'interpréteur (tests + fuzzer aléatoire, qui a aussi trouvé deux bugs de l'interpréteur) ; ~6 instructions ARM par instruction PPC (entier), ~10,6 (flottant) sous qemu. À faire : mesurer sur le Pi, tester sur de vrais jeux (dump de son propre disque à fournir), son (DSP AX en HLE), cartes mémoire. |
| GPU V3D | ✅ | Validé sur le Pi : 6400 triangles, 2,1 ms par image avec le GPU (174 images/s) contre 13,4 ms en logiciel. Pilote noyau `sys/v3d.cpp` (kapi v52 `gpu_info` / `gpu_draw`) : mise sous tension (firmware + PM/ASB), listes binner / renderer, shaders QPU précompilés (exemples Random06457, MIT), test de profondeur, attente par compteurs avec délai max ; démo `teapot` (théière de l'Utah, 6400 triangles, repli logiciel). **Pipeline complet (kapi v53, validé sur le Pi : `gpudemo` 191 images/s, 1,6 ms)** : textures RGBA8 (dispositions LT / UBLINEAR / UIF / XOR de Mesa, test hôte), lots (batches) avec matrice 4 × 4 appliquée par le GPU, blending alpha / add / mul, test de profondeur et culling ; shaders écrits à la main en assembleur QPU (`tools/qpu/qpuasm` : encodeur Mesa + validateur des contraintes) ; démo `gpudemo`.
